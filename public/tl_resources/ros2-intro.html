Introduction to ROS2

Architecture, core concepts, and how to move between ROSpad and a real ROS2 installation.

What is ROS2?

ROS2 stands for Robot Operating System 2 — but don't let the name fool you. It is not an operating system. ROS2 is a middleware framework: a layer of software that sits between your robot's hardware drivers and your high-level application code, handling communication, discovery, and message passing.

Think of it as a shared language and postal system for robot software components. Each component (a camera driver, a path planner, a motor controller) runs as a separate program. ROS2 lets them find each other and exchange data without knowing anything about each other's implementation.

Key insight

ROS2 does for robots what TCP/IP does for computers on a network: it defines how messages are addressed, routed, and delivered — so your algorithms can focus on what to compute, not how to talk to each other.

Why ROS2 (not ROS1)?

ROS2 was designed from the ground up to fix the limitations of ROS1:

  • No single point of failure: ROS1 required a central roscore process. ROS2 uses DDS (see below) for fully distributed discovery.
  • Real-time capable: ROS2 supports real-time scheduling and deterministic messaging where needed.
  • Security: Built-in support for encrypted, authenticated communication.
  • Multi-platform: Works natively on Linux, Windows, and macOS.
  • Quality of Service (QoS): Fine-grained control over reliability, history, and latency.

Nodes

A node is a single executable program — one process, one purpose. A robot system typically has many nodes running simultaneously:

  • A camera_driver node reads frames from a USB camera and publishes them
  • A lidar_driver node reads laser scan data
  • A slam_node node subscribes to lidar data and builds a map
  • A path_planner node subscribes to the map and publishes velocity commands

Nodes are written in Python or C++. In Python, every node inherits from rclpy.node.Node:

my_node.py
import rclpy from rclpy.node import Node from std_msgs.msg import String class MyNode(Node): def __init__(self): super().__init__('my_node') # node name self.pub = self.create_publisher(String, '/chatter', 10) self.timer = self.create_timer(1.0, self.tick) def tick(self): msg = String() msg.data = 'Hello!' self.pub.publish(msg) self.get_logger().info('Published: Hello!') def main(): rclpy.init() rclpy.spin(MyNode()) if __name__ == '__main__': main()

Topics

Topics are named, typed, asynchronous data streams. Any node can publish to a topic; any node can subscribe to a topic. Neither knows about the other — they only know the topic name and message type.

  • Name: a slash-separated path like /camera/image_raw or /cmd_vel
  • Type: a message type like sensor_msgs/Image or geometry_msgs/Twist
  • Pattern: publish-subscribe — one publisher can have many subscribers

Common message packages: std_msgs (primitives), geometry_msgs (vectors, poses), sensor_msgs (cameras, lidar, IMU), nav_msgs (maps, odometry).

Services & Actions

⟺

Services

Synchronous request–response. One node calls a service, another handles it and returns a result. Good for short, fast operations: "What is the current joint angle?"

⟳

Actions

Like services, but for long-running goals. The caller gets progress feedback and can cancel mid-flight. Good for: "Navigate to this waypoint" or "Pick up this object."

⚙

Parameters

Named, typed configuration values per node. Can be set at launch time or changed at runtime: loop_rate, max_speed, threshold. Read with declare_parameter().

DDS & Middleware

Under the hood, ROS2 uses DDS (Data Distribution Service) for all communication. DDS handles node discovery (how nodes find each other on the network), serialization, and delivery guarantees.

You rarely interact with DDS directly, but you should know about Quality of Service (QoS) profiles, which control how messages are delivered:

  • Reliability: RELIABLE (guaranteed delivery, like TCP) vs BEST_EFFORT (fast but lossy, like UDP)
  • History: how many past messages to buffer for late subscribers
  • Durability: whether messages persist for nodes that haven't started yet
ROSpad note

ROSpad replaces DDS with a BroadcastChannel-based message bus running in the browser. The API (topics, services, pub/sub) is identical — DDS discovery and transport are simulated. QoS settings are accepted but not enforced. Services are fully implemented: create_service / create_client / call_async all work as in real rclpy. Try the service_demo package for a hands-on example.

Getting Started on ROSpad

On ROSpad, the full ROS2 workflow runs in the browser. Here is the standard flow:

Create a package

A package bundles related nodes and their dependencies. Use ros2 pkg create --build-type ament_python my_package in the terminal.

Create and write your node file

Use touch src/my_package/my_package/my_node.py then open it in the editor. Write your Node class with publishers, subscribers, and timers.

Register the entry point in setup.py

Edit src/my_package/setup.py and add 'my_node = my_package.my_node:main' under console_scripts.

Build

Run colcon build. In ROSpad this indexes your packages so ros2 run can find them.

Run your node

Use ros2 run my_package my_node. The node opens in its own terminal tab. Check output with ros2 topic list and ros2 topic echo /topic_name.

Migration Guide

ROSpad → Real ROS2

When you're ready to move your code to a real machine:

Install ROS2

Follow the official docs for your OS at docs.ros.org. Humble (LTS) or Iron are recommended for new projects.

Copy your package files

Download your package folder from ROSpad (file tree → ⬇ button) and place it in your ros2_ws/src/ directory.

Install dependencies

Run rosdep install --from-paths src --ignore-src -r -y to install any missing packages.

Build with colcon

Run colcon build then source install/setup.bash. The shell overlay makes your packages visible to ros2 run.

Run and verify

Use ros2 run my_package my_node and ros2 topic echo /topic just like in ROSpad.

Real ROS2 → ROSpad

Bringing an existing ROS2 Python node into ROSpad:

Check for unsupported features

Services, actions, parameters, lifecycle nodes, and tf2 are not fully supported. Simplify or stub these out.

Remove unsupported imports

ROSpad includes rclpy, std_msgs, geometry_msgs, sensor_msgs, and nav_msgs. Remove other package imports.

Upload and run

Create a package in ROSpad, paste your node file, register it in setup.py, and colcon build.

What to Keep in Mind

Threading model

On a real system, rclpy.spin() blocks the calling thread to process callbacks. In ROSpad, spin() exits immediately — timers and callbacks are driven by the browser's JS event loop. Your code logic is the same; the machinery underneath differs.

Concurrent nodes share a Python runtime

In real ROS2, each node is a separate process. In ROSpad, each node runs in its own Web Worker with its own Pyodide instance — effectively separate processes. Global state is NOT shared between nodes.

Naming conventions

Topic names in ROS2 use snake_case and start with / for absolute names or no slash for relative names. In ROSpad, always use absolute names (starting with /). Example: /cmd_vel, /scan, /robot_description.

Good news: the API is the same

The code you write in ROSpad — node classes, publishers, subscribers, timers, logger calls — runs unchanged on a real ROS2 installation. The learning you do here transfers directly.
