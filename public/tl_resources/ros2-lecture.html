Core Concepts

A Node in Python

import rclpy from rclpy.node import Node from std_msgs.msg import String class Talker(Node): def __init__(self): super().__init__('talker') self.pub = self.create_publisher( String, '/chatter', 10) self.create_timer(1.0, self.tick) def tick(self): msg = String() msg.data = 'Hello!' self.pub.publish(msg) def main(): rclpy.init() rclpy.spin(Talker())
  • Inherit from Node — provides the ROS2 context
  • create_publisher: bind to a topic and message type
  • create_timer: call tick() every 1 second
  • spin(): hand control to the event loop — callbacks fire from here
  • A node can have multiple publishers, subscribers, timers, and services simultaneously
Core Concepts

Publish / Subscribe

Sender and receiver are completely independent. They share only a topic name and message type.
# Publisher side self.pub = self.create_publisher( String, '/chatter', 10) self.pub.publish(msg) # Subscriber side self.sub = self.create_subscription( String, '/chatter', self.callback, 10) def callback(self, msg): self.get_logger().info( f'Heard: {msg.data}')
  • The 10 is queue depth — how many messages to buffer
  • Message types live in packages: std_msgs, geometry_msgs, sensor_msgs
  • Topic names are namespaced: /robot1/cmd_vel isolates robots
  • Try it: run talker, then ros2 topic echo /chatter
Core Concepts

Services & Actions

Not everything is a continuous stream. Some interactions are request–response.
Services — synchronous call
  • Client sends a Request, server returns a Response
  • Use for: queries, mode changes, one-shot actions
  • Examples: /set_mode, /get_state
  • Blocks the caller until response arrives
Actions — long-running goals
  • Like a service, but returns feedback while executing
  • Can be cancelled mid-flight
  • Use for: navigation, manipulation, any multi-second task
  • Examples: NavigateToPose, GripperCommand
Rule of thumb: Use topics for continuous data streams. Use services for quick queries. Use actions for long tasks that need feedback.

Building

Real-world ROS2 you'll encounter

  • Namespaces: prefix all topics with /robot_name/ to run multiple robots on the same network
  • QoS profiles: use BEST_EFFORT for sensor streams (speed), RELIABLE for commands (correctness)
  • Lifecycle nodes: manage startup/shutdown of critical hardware nodes — unconfigured → active → deactivating
  • Launch files: .launch.py scripts start many nodes at once with configurable parameters
  • tf2: the transform library — tracks coordinate frames over time. Essential for sensor fusion and manipulation
  • rqt & rviz: GUI tools for visualising topics, images, robot state — the ROS2 dashboard
URDF

One file, every tool

URDF — Unified Robot Description Format. An XML file that is the single source of truth for your robot's geometry, joints, and sensors.
What it captures
  • Links — rigid bodies: visual shape, collision hull, mass & inertia
  • Joints — connections between links: type, offset from parent, rotation axis, motion limits
  • Sensors — cameras, lidar, and IMUs declared inline
  • Materials — colours and textures for visualisation
  • Inertial — mass, centre of mass, inertia tensor for physics simulation

URDF

Links and Joints

A URDF is a kinematic tree. Links are rigid bodies; joints define how they connect and move.
A Link has three sub-elements
<link name="forearm"> <visual> <!-- what students see --> <origin xyz="0 0 0.175"/> <geometry><box size="0.04 0.04 0.35"/></geometry> </visual> <collision> <!-- physics hit shape --> <geometry><box size="0.04 0.04 0.35"/></geometry> </collision> <inertial> <!-- mass and inertia for dynamics --> <mass value="0.8"/> <origin xyz="0 0 0.175"/> </inertial> </link>
Joint types
TypeMotionTypical use
revoluterotates, limited rangeshoulder, elbow, wrist
continuousrotates, no limitswheel, propeller
prismaticslides along axislinear actuator, gripper rail
fixedrigid — no DOFcamera mount, sensor bracket
Key joint elements
  • <parent> / <child> — which links it connects (directed: parent → child)
  • <origin> — offset from parent frame to child frame — effectively the link length
  • <axis> — unit vector the joint rotates or slides along
  • <limit> — min/max in radians (revolute) or metres (prismatic)
URDF

A 3-DOF arm in URDF

Three revolute joints chained in series. Each <joint> origin encodes the link length; the axis element defines which way it bends.
Kinematic tree
base_link
└─ joint1 → link1
    └─ joint2 → link2
        └─ joint3 → link3
rrr_arm.urdf
<robot name="rrr_arm"> <link name="base_link"> <visual><geometry> <cylinder radius="0.05" length="0.1"/> </geometry></visual> </link> <link name="link1"> <visual><origin xyz="0 0 0.2"/> <geometry><box size="0.04 0.04 0.4"/></geometry> </visual> </link> <!-- link2, link3: same pattern, different sizes --> <joint name="joint1" type="revolute"> <parent link="base_link"/> <child link="link1"/> <origin xyz="0 0 0.05"/> <!-- top of base cylinder --> <axis xyz="0 0 1"/> <!-- pan: rotate about Z --> <limit lower="-3.14" upper="3.14" effort="10" velocity="1"/> </joint> <joint name="joint2" type="revolute"> <parent link="link1"/> <child link="link2"/> <origin xyz="0 0 0.4"/> <!-- end of link1 (= its length) --> <axis xyz="0 1 0"/> <!-- pitch: rotate about Y --> <limit lower="-1.57" upper="1.57" effort="10" velocity="1"/> </joint> <joint name="joint3" type="revolute"> <parent link="link2"/> <child link="link3"/> <origin xyz="0 0 0.35"/> <!-- end of link2 --> <axis xyz="0 1 0"/> <!-- pitch: rotate about Y --> <limit lower="-1.57" upper="1.57" effort="10" velocity="1"/> </joint> </robot>

ROSpad extras — same URDF, browser aware
Two Gazebo-compatible plugin blocks in the URDF give ROSpad everything it needs — no sim.js changes required:
Camera sensor → publishes image topic
<gazebo reference="camera_link"> <sensor type="camera"> <horizontal_fov>1.047</horizontal_fov> <image><width>320</width><height>240</height></image> <plugin name="rospad_camera"> <remapping>~/image_raw:=/camera/image_raw</remapping> </plugin> </sensor> </gazebo>
Bridge plugin → declares topic names
<gazebo> <plugin name="rospad_bridge"> <subscribe topic="/joint_states" type="sensor_msgs/JointState"/> </plugin> </gazebo>
Any URDF with these blocks works in ROSpad automatically. Add a new robot package with its own URDF and it just works.

Vision: cameras as topics

A camera is just a node that publishes sensor_msgs/Image — image data is a NumPy array.
How it works
  • Declare a <sensor type="camera"> in URDF
  • Simulator auto-publishes /camera/image_raw at 10 Hz
  • Click the topic in the Topics panel — see a live preview
  • Subscribe in Python → np.asarray(list(msg.data), dtype=np.uint8).reshape(h,w,3)
colour tracker pattern
  • Threshold by RGB: R>150 & G<80 & B<80
  • Find centroid with np.where(mask)
  • Compute horizontal offset → angular.z
  • Robot steers toward the coloured target — visual servoing
